# Taste
- For the dashboard UI (both user and admin dashboards), use Inter as the font family throughout — for body text and headings/display alike. Load it from https://rsms.me/inter/inter.css. (This supersedes an earlier DM Sans preference.) Confidence: 0.9
- Drives UI work from reference screenshots/mockups and expects the implementation to visually match them (layout, icons, colors, connectors) and to include the interaction/hover states too — including calling out that specific icons must be the exact ones shown in the reference. Confidence: 0.9
- Wants shared, reusable layout elements applied globally across a section rather than duplicated per page — e.g. a single footer component rendered on every user dashboard page. Confidence: 0.8
- For link/nav lists (e.g. footer link groups), prefers them stacked vertically in a single column rather than laid out side-by-side in a multi-column grid. Confidence: 0.5
- Prefers real brand assets/logos over placeholder stand-ins (e.g. colored initial tiles) for partner/brand displays. Confidence: 0.5
- Works screen-by-screen on the redesign, building out one screen/section at a time. Confidence: 0.7
- Wants visual parity across breakpoints and supplies both a mobile and a desktop mockup in the same message, expecting the page rebuilt to match both (e.g. "rebuild X to look exactly like this on mobile and desktop"). When a treatment is shown for mobile (e.g. a card container wrapping a group of links), expects it applied on desktop too, not diverging per breakpoint. Confidence: 0.7
- When replicating a reference section, may paste the original source markup/CSS and expect it reconstructed faithfully — preserving exact values (coordinates, animation durations/delays, the original @keyframes) rather than approximations. The pasted markup is often compiled/rendered DOM from a React+Radix/shadcn build (e.g. `data-state`, `radix-*` ids, `ring-offset-background`/`bg-secondary` tokens, hashed asset filenames like `badge-normal-C3gnJw33.png`); expect it translated faithfully into Blade/Livewire, with hashed asset references mapped to the project's actual local files (and noting when an asset is missing). Confidence: 0.75
- Supplies design assets (logos, images, SVG markup) by pasting them directly into the chat rather than committing files to the repo; when a page/section has multiple images he sends them as an ordered set ("these are the images from the page in order") and expects them mapped into the page's image slots in that exact sequence. Pasted images aren't reliably retrievable from disk, so wiring exact target filenames/paths and having the user drop the files in can be required — he's fine saving them into the project's expected paths himself. Confidence: 0.85
- On mobile, prefers to avoid truncated labels: shrink font size and/or tighten padding so text fits fully on one line, reserving ellipsis for only the longest label (e.g. "Certificate"). Confidence: 0.6
- Iterates on the redesign by sending mobile screenshots and expects the mobile layout to match them — including condensed mobile variants where elements are resized down or hidden on small screens (e.g. the "Why Us" descriptions hidden on mobile, shown on desktop) while the structural layout stays consistent across breakpoints. Confidence: 0.7
- For sections that would otherwise stack to a single column on mobile, keeps them as a condensed multi-column grid on mobile instead (e.g. Why Us 3-across, brand partners 2-up, dashboard stat cards 2-up), often with a featured/primary item spanning the full width and centered/below. When requested, scopes such layout changes to the mobile breakpoint only, leaving the wider breakpoint's layout (e.g. 3-across on desktop) untouched — implemented mobile-first with responsive utility variants (e.g. `grid-cols-2 ... sm:grid-cols-3` plus `col-span-2 ... sm:col-span-1`). Confidence: 0.7
- Maintains several sibling Laravel/Livewire projects on the same machine (Herd) and expects the agent to lift an existing implementation from another project (e.g. "find this iframe implementation on the support section of the account page of fxtbot and implement it here") rather than reinvent it — reusable patterns/features should be ported across his projects to match. Confidence: 0.6
- Does not want tests or console commands to be able to wipe his local dev database; expects the test suite to be isolated (e.g. in-memory SQLite) and destructive DB operations (`migrate:fresh`/`RefreshDatabase`) kept off real local data, and cares about preserving the local dev accounts/data he's using. Confidence: 0.55
- Prefers modals/dialogs to be centered on screen (positioned via `left-1/2 top-1/2 -translate-x/y-1/2`, with a fade/scale transition and a dimmed backdrop) rather than presented as a bottom-sheet that slides up from the bottom edge. Confidence: 0.6
- Prefers in-page modals over navigating/redirecting to a separate page for the first step of a step flow (e.g. clicking START opens a task modal on the same page instead of redirecting to `/dashboard/optimize`), and expects the existing functionality/logic rebuilt to run inside the modal rather than left on the old page. Nuance: the modal is treated as a one-shot action — once a task is already pending, prefers redirecting to the records/listing page to surface that status (a tappable card that opens the submit modal) instead of re-opening the modal on every trigger. Confidence: 0.6
- Expects modals to open only on explicit user action (e.g. clicking START), not auto-open on page load/reload — a pending/lingering state (in session or otherwise) shouldn't re-trigger the modal every time the page mounts. Confidence: 0.5
- For active/selected states of nav links (e.g. the mobile bottom bar), prefers a translucent pill background — the accent color at reduced opacity (e.g. `bg-sidebar-primary/20`) — with the icon rendered in the solid accent color, instead of a fully-filled solid pill; also prefers a generous/large border radius for the encompassing pill (e.g. `rounded-xl`). Confidence: 0.55
- Wants comfortable horizontal padding/whitespace around dashboard page content so text and images don't hug the viewport edges — while full-bleed elements (e.g. a tab row whose underline runs edge-to-edge) are still expected to span the full width to match the reference. Confidence: 0.5
- For notice/announcement callout boxes, prefers a green treatment (e.g. light-green background with green border and green text, plus dark-mode variants) instead of a neutral muted/gray box. Confidence: 0.45
- Dislikes text-derived placeholder avatars: for the profile/avatar, prefers a generic icon over the user's initials, and specifically wants a self-contained "circled user" glyph (e.g. lucide `circle-user-round` — a person inside a ring) rather than composing a plain user icon on a filled/colored circle background; also cleans up now-unused computations when swapping it in. Confidence: 0.65
- For transient notifications/toasts, prefers them anchored at the bottom of the screen on mobile (full-width, sitting just above the mobile bottom nav) and bottom-right on desktop — rather than centered/top. Confidence: 0.5
- For toasts, expects entry/exit motion to match the bottom anchoring: slides up when entering and slides down when leaving (not a fade/scale). Confidence: 0.55
- For list/history displays (e.g. completed/submitted tasks), expects the populated state wrapped in a card container styled consistently with the empty state — items inside a bordered/elevated card (`card-elevated rounded-lg border bg-card shadow-sm`, `divide-y` between rows) rather than left bare on the page. Wants such containers to carry a labeled header (a small section title row with a bottom divider, e.g. "Completed"). Paginates long lists at 10 items per page, sorted most recent first (`latest()`), with the paginator rendered directly below the container (centered). Confidence: 0.65
- Expects contextual status indicators/banners to render only when their underlying state actually applies — e.g. a "PENDING PRODUCT" alert in the task modal should appear when opening an already-pending submission but NOT on the first-time START click when there's no existing pending product; expects this gated by an explicit conditional flag rather than always rendered. Confidence: 0.5
- Redesigns are expected to be full-stack: when he asks to rebuild/redesign a page he wants the backing schema and functionality changed to match ("modify the db schema and functionality to match these new specifications") — new migrations, model/factory updates, backend actions and tests — not just the Blade view. Confidence: 0.6
- Prefers routes/pages named after the user-facing feature term (e.g. renamed `/dashboard/alerts` → `/dashboard/notifications`) and expects every reference updated (route definition, nav config, layout header, account links) so no stale old names remain. Confidence: 0.5
- For notification/list items with read state, distinguishes unread from read: unread items get a subtle highlight (light/primary-tinted background plus a border) while read items are plain, and clicking an item marks it read. Confidence: 0.5
